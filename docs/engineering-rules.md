# Agent Plan 工程规则草案

适用范围：总工作区、agent-plan-core、agent-plan-cli。本文是本轮审查后的规则建议，尚未作为 AGENTS.md 自动执行。

## 1. 完整交付当前范围

- 先明确输入、输出、错误、资源生命周期和验收条件，再实现功能。
- 已承诺的能力必须完成正常、失败和清理路径；禁止假成功、静默降级和以 TODO 代替关键实现。
- 不为未确定的需求提前建设通用框架。恢复执行、交互调试、远程服务不属于当前 CLI 范围。
- 改变公开行为时同步更新协议、文档、示例及行为测试，不长期保留两套实现。

## 2. 复用优先

- 先检查现有公共能力，再选择标准库，最后评估成熟第三方包。不要重写通用命令解析、格式化、HTTP 客户端或测试框架。
- core 当前无第三方运行时依赖；保持轻量，但零依赖不是阻止正确选型的硬指标。
- CLI 扩展多命令时可使用 Commander 管理命令、选项和帮助；文件、流、HTTP 优先使用 Node 标准能力。
- 引入依赖须说明解决的问题、为何标准库不足，并检查许可证、维护情况、Node 24 和 ESM 兼容性；开发工具放入 devDependencies。
- 不使用包的未公开内部路径；CLI 只能从 core 的公开入口导入。

## 3. 明确职责

- core：流程结构、校验、字段语义、节点执行、调度、状态及结构化错误。
- CLI：命令协议、输入加载、宿主函数加载、输出编码、trace 落盘、进程退出及资源释放。
- core 不依赖 CLI，不直接读写文件、控制终端或维护历史快照。
- 外部 HTTP、模型和数据库能力由宿主函数提供。
- 同一份流程语义只维护一次；CLI 的 inspect、validate、run 复用 core 的公共分析和校验能力，不复制规则。

## 4. 按职责拆分代码

- CLI 入口仅组装命令并处理进程边界；命令实现、输入加载、执行驱动、结果协议、trace 各有清晰归属。
- core 的纯节点计算与调度可分开；共享忙碌锁、调用栈和子流程返回提交仍由统一调度逻辑维护。
- 不按机械行数拆文件，不为单次使用创建泛化框架，不堆积无明确职责的 utils。
- 外部输入先以 unknown 接收，校验后再取得类型；类型断言不能代替运行时校验。

## 5. 保持已确定语义

- 未初始化字段为 undefined；缺失输出属性写入 undefined；运行时允许任意 JavaScript 值。
- 同一调度器的 step、run 和字段修改遵守忙碌保护；子流程字段隔离及对象引用语义不得由 CLI 悄悄改变。
- trace 不改变正常执行结果，不保存可继续变化的对象引用作为历史。
- 记录和恢复是不同协议：未保存完整可恢复状态时，不承诺可重放或恢复执行。

## 6. CLI 是稳定的进程接口

- 机器输出有版本和固定的成功、失败结构；错误保留错误码、流程实例、步骤位置和可用的调用栈。
- 明确 stdout、stderr 和退出码约定；机器模式的 stdout 不混入日志或进度。
- 宿主模块导入和执行都可能产生输出，必须纳入输出隔离设计，不能仅约定主程序不用 console.log。
- 文件、内联 JSON、stdin 的输入优先级或互斥关系明确；不依赖未声明的工作目录或自动猜测输入来源。
- JSON 结果、可读文本、trace 摘要各自定义用途。undefined、循环引用、二进制、getter 和 toJSON 的处理必须明确，不把有损摘要称为无损快照。

## 7. trace 和运行限制必须可靠

- trace 增量写入，记录顺序、实例、步骤、耗时及失败；处理背压、写入失败和结束时刷写。
- 如使用字段差量，必须处理对象原地修改和子流程返回时的父字段变化，不能只比较引用或只观察当前栈顶。
- 对记录的深度和大小设限，截断显式标记；不默认输出敏感输入和完整二进制。
- 超时必须明确终止范围；Promise.race 只停止等待，不能作为已终止执行的实现。
- 若承诺强制中止任意宿主代码，需要可终止的执行边界；合作取消只承诺已支持的宿主能力。外部副作用不能视为已回滚。

## 8. 自动验证和仓库管理

- 使用现有 node:test，测试可观察行为、失败路径及关键边界，避免镜像实现细节。
- 采用一种成熟格式化和 lint 工具，例如 Biome；通过 CI 执行格式、lint、类型、构建和相应测试。
- CLI 协议测试覆盖实际子进程、stdout/stderr、退出码；有 trace 或超时时增加对应集成测试。
- 子仓库不依赖总仓库未声明的测试文件。workspace 依赖限制必须明示，独立仓库不等于可独立安装的 npm 包。
- 先提交、推送子仓库，再提交总仓库指针；检查依赖锁文件和子模块提交可获取，不提交构建产物、临时文件及凭证。

## 初次审查结论（实现前）

- core 无第三方运行时依赖，已有结构、类型、校验、值语义等模块划分，符合轻量定位。
- CLI 目前只有 run，约 100 行的入口可用于现有规模；扩展前应拆分职责，不能继续将所有能力加入 index.ts。
- CLI 将 runtime 失败转换为字符串，机器错误协议尚未建立。
- 宿主模块在 CLI 进程内导入和调用，stdout 尚无隔离保证。
- CLI checkJson 与 core copyJson/isJsonData 各自维护 JSON 边界，需明确共同语义与各自用途，避免继续复制。
- core 的校验函数目前未通过公开入口导出；新增 inspect/validate 时需设计公共能力。
- 当前脚本有构建、类型检查和测试，未发现格式化、lint 及 GitHub Actions 工作流。
- CLI 仍依赖 workspace:*，不是可独立安装的发布包；已有说明，后续发布必须真正验证安装链路。

以上为制定规则时的静态审查记录。

## 本次落地

- CLI 已按命令组织、输入、执行子进程、父进程控制、协议、trace 写入和摘要拆分模块。
- Commander 管理多命令和选项；文件、进程及 IPC 使用 Node 标准库。
- core 公开 parseFlow、inspectFlow、toJsonValue；CLI 不复制流程校验或 JSON 值规则。
- 子进程隔离宿主 stdout；机器成功/失败统一使用协议 v1。
- 支持文件、内联 JSON 和 stdin 输入，run、inspect、validate，以及逐步 trace 和可终止的执行超时。
- trace 的值采集需显式开启，摘要有边界，不执行 getter/toJSON，不承诺恢复。
- 根工作区提供 Biome 和 pnpm verify，CI 验证 Windows/Linux 上的固定子模块组合。
- 保持 workspace 开发方式；npm 发布、交互调试和恢复执行仍不在本次范围内。
